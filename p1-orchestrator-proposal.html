P1 MCP SERVER · ALTERNATE CONSUMPTION PATTERN

Specialists over the raw tool supply

A reference implementation — built and run against a live PingOne tenant — of an intent layer above the PingOne MCP Server: one admin intent in, a specialist agent plans and executes the raw tool calls, and the caller never touches the 78-tool catalog.

Chris Price · Identity Architecture 2026-09-21 Reference implementation: p1-orchestrator

The problem: 78 tools, no procedure

The PingOne MCP Server exposes 78 tools spanning every service — the right surface for a human-driven generalist, and a poor one for any agent asked to complete real work:

  • Schema tax. All 78 tool definitions ride in the model's context on every turn, whether or not the task touches them.
  • No procedural knowledge. Tool descriptions say what each tool does; none say how tools chain. The knowledge that OIDC scopes live on Resources and get granted to Applications — via a second round-trip through updateApplication with a createGrant operation — is tribal. Every consumer rediscovers it, or gets it wrong.
  • Cross-service flows have no home. The "onboard an application" task spans Applications + Resources + scopes. A tool catalog sliced by service cannot express it; skills patch this by extending context — the same tax, paid again.

The thesis: the tool subset is only half the win. The other half is the playbook. A specialist with 10 tools and a written procedure outperforms a generalist with 78 tools and none — and the subset is data, so the pattern survives every tool Ping adds.

The pattern

Three layers, each doing one job:

Client (Claude Code · IDE · any MCP client) │ sees 3 fixed tools — directory + dispatch + env lookup, never the 78 schemas ▼ Orchestrator MCP Server — this repo, ~500 lines │ list_specialists returns the live set from the registry; │ dispatch_specialist routes intent → specialist, resolves auth & │ environmentId once per call: fresh agent loop, own persona, own subset ▼ Specialist — bounded LLM loop, playbook + tool subset │ e.g. app_onboarding: 13 of 78 tools, procedure in its prompt ▼ PingOne MCP Server — unchanged, raw tool supply │ ▼ PingOne platform

Each specialist is defined declaratively — name, routing one-liner, tool subset, playbook. The launcher computes the tool deny-list as the complement of the subset against the live catalog, so upstream changes to the PingOne server require no change here:

app_onboarding (13 of 78 tools):
  listApplications · getApplication · createApplication · updateApplication
  deleteApplication · listApplicationCatalog · listResources · getResource
  createResource · updateResource · deleteResource · listEnvironments
  getEnvironment

+ playbook: resolve resource → create app → grant scopes → verify
+ shared rules: secrets masked · env hoisted · confirm destructive ops

The specialist set itself is one JSON file per specialist — routing one-liner, tool subset, corpus topics, optional pingcli fallbacks, playbook. All six live in specialists/, versioned with the code; a specialist is added by writing a file, never by editing TypeScript or recompiling:

Auth composes — nothing new to invent

The orchestrator is itself a conforming MCP client of the PingOne MCP Server, so it runs the same authorization the server already supports — the pre-wired pingone-mcp-server client, OIDC authorization code + PKCE, the admin signing in as a person in a browser once. Tokens cache and refresh; the human never sees the browser again until refresh-token expiry. An unattended (worker-app, client-credentials) arm is available for headless deployments; both resolve through one interface, chosen at config time:

Admin-person OAuth (default)     Worker app (headless)
  browser login, once              client credentials
  identity = the human admin       identity = service principal
  audit trail: named person        audit trail: the service
  role-scoped in PingOne           role-scoped in PingOne

Worked example 1 — create. Intent: "Create an OIDC web app named orchestrator-probe-app with scopes openid, profile, email, PKCE enforced, redirect localhost:3000/callback, enabled." The specialist created the app, located the openid Resource, granted the three scopes as a grant, verified by read-back, and reported — including which things it deliberately left undone and how to retrieve the secret it cannot see. Independently verified field-by-field afterward.

Worked example 2 — update. Intent: "Add redirect URI http://localhost:8081/oidc/callback, keeping all existing config." Three tool calls: filtered lookup, array-preserving update (it knew redirectUris replaces, not merges), verify. The report enumerated everything confirmed unchanged — including the scope grant from example 1.

What the caller saw in both cases: one tool call with one sentence of intent, then a compact report with every ID touched. What the platform saw: a scoped, named human identity making conventional API calls.

Visibility, by design

Specialists are not black boxes. Every run emits all three lenses:

  • Live — MCP progress notifications stream each tool call and narration as it happens.
  • Audit — a structured NDJSON run log per execution: every call with arguments, timestamped, grep-able.
  • Interactive — each run returns a session id; the specialist can be resumed and interrogated afterward.

The registry story: built-ins, drop-ins, one format

The six specialists did not all start the same way — and the history is the lesson. Three were born as compiled TypeScript entries in registry.ts ("built-ins"); the next three arrived after the scaling question ("can specialists scale as the P1 MCP tools expand into their domains?") as JSON files dropped into a directory outside the repo ("drop-ins"). Two formats, one merged list, an override rule to reconcile them — construction order showing through as architecture. The unification became its own proof point:

  • One format won: JSON. Nothing about a specialist benefits from being code — the playbook is prose, the tool subset is a string array. Adding a specialist became writing one file: no TypeScript, no recompile, no redeploy. registry.ts is now just the interface, the shared rules, and a two-directory loader.
  • One set won: all six are product. Every specialist here encodes transferable domain knowledge — the MFA binding graph (policies bind to Protect mitigations and DaVinci flows, never to applications), the Protect method choice, the auditor's always-set-explicit-dates rule. That's the product's knowledge, so all six live in specialists/, versioned with the code. A clone of the repo works out of the box — no "also copy these three files" step. That's the difference between shipping a reference and shipping a demo.
  • The local directory stayed, with a precise job: personal overrides and playbook experiments only (drop-in wins on name clash, 30s TTL reload). Try a playbook edit there before committing it; park a tenant-specific specialist you wouldn't ship.
  • Dynamic exposure was verified in both directions before unification: a file dropped in appears in the directory on the next listing with no server restart and no client reconnect; deleting the file retracts it the same way. Retraction is the property a compiled built-in list can't offer.

The fixed 3-tool client surface makes the dynamic set safe to expose: adding a specialist never renegotiates the client connection — it surfaces in the list_specialists directory's output, never in the tool listing. Fixed contract, dynamic content.

The knowledge story: where does a specialist learn "the What"?

Tool descriptions say what each tool does; they cannot say how tools chain or which constructs combine. Ping's docs hold those answers — and Ping is already agent-ready (llms.txt indexes, token-efficient .md alternates, a docs-for-agents guide) — but no artifact binds docs to actions. We hit this concretely: the task "create a token-exchange app with a custom audience" produced a Worker app, and the platform rejected it (CONSTRAINT_VIOLATION). The constraint — worker apps can only hold grants on the openid resource; custom audiences ride on Resource scopes for non-worker apps — lives in the platform's behavior, partially in the docs, fully in neither the tool descriptions nor the API reference. Our first version learned it from a 400. The fix became an architecture:

Orchestrator at dispatch — it is a retrieval layer, not just a router │ │ 1. ROUTE intent → specialist │ 2. GATHER situational knowledge: │ tier 1 — curated pins (16 hand-picked pages; the authority floor) │ tier 2 — P1 Docs MCP (docs.pingidentity.com/mcp — agent-fronted │ semantic retrieval over the live corpus, docset-filtered; zero local doc URLs, new pages discoverable on publish) │ 3. DISTILL bounded decision-relevant excerpts (sourced, dated) ▼ Specialist receives: intent + environmentId + SITUATIONAL CONTEXT │ playbook owns procedure · context owns the facts of this task │ ground truth remains the tool catalog + PingOne enforcement

The division of labor is the point: the orchestrator knows where knowledge lives, the context carries what's true for this task, the playbook owns what to do, and PingOne stays the enforcement authority. None of it is duplicated.

The auditor: the newest specialist, the clearest lesson

The sixth specialist was born the way the pattern predicts — a gap noticed mid-task. "What did we get up to in this environment over the last two days?" had no specialist to route to, so one was written as a JSON file and dispatched to answer the question that prompted it, the same hour. Three findings from that run carry the story:

  • The supply was already there. The P1 MCP catalog already ships searchAuditActivities + getAuditActivity — so the auditor is the first specialist with zero pingcli fallback: pure native supply, and the first domain where the bridge has retired itself entirely. What was missing was only the procedure that knows to reach for them.
  • The playbook beat the hand-written query. The direct API call the same question prompted first used since= — which PingOne silently narrowed to ~24h (55 events). The specialist, following its own always-set-explicit-dates rule, swept the true two-day window (73 events) and caught a Sep 21 user-lifecycle chapter the direct call missed entirely. The MCP tool's own description warns about exactly this; a playbook turns a warning into a behavior.
  • The trail also validated the attribution story. Every specialist action appeared under the admin person identity via pingone-mcp-server; the console checks appeared via adminui; the bridge calls carry the PingCLI worker. Two channels, clean separation, already in the audit trail — and the auditor itself explained the one scary-looking cluster (13 secret reads in 3 seconds) as the MFA specialist's batched application-detail fetches, cross-checked against run logs.

The same A/B also surfaced the honest edge: on one run the specialist still reasoned worker-first (the docs don't mandate an app type), hit the constraint, dry-run-deleted its own stub, recreated correctly, and reported the doc-vs-API conflict explicitly — "reported, not forced." Self-recovery is good; it also demonstrates why the learnings loop matters: the specialist cannot remember across runs, only the corpus can. A single learned pin ("workers can't hold custom-resource grants") converts that recovery story into a first-pass story — that is the highest-value next artifact, and it is ours to write.

The corpus is a workaround for a missing P1 artifact

Everything above runs on a hand-curated map of 16 pinned pages plus semantic retrieval — and that is the strongest form of the ask: Ping ships the corpus and the index; the one binding agents need is which pages decide which task. Two publishable shapes, both with working consumers in this repo:

  • A topic map — task/tool → the 1–3 authoritative pages, publishable next to the llms.txt indexes. Our local map (corpus.ts) is the client; npm run pin-check is the freshness contract.
  • Per-tool doc bindings — a docs field in the MCP catalog itself (createApplication → applications-1.md + token-exchange-grant-type.md). One line per tool; the binding arrives with the schema and needs no separate artifact.

And the docs server under development closes the loop from the other side: with agent-fronted retrieval live, this repo's local curation demotes to pins-and-learnings the moment the service productizes — the consumption code already speaks to it.

How the intent layer scales as the catalog grows

The catalog is growing: ~78 platform tools today, and a plausible all-services landing (adding Protect, MFA, Credentials, Verify, Authorize, SSO policy) puts it well past 140. At that scale the intent layer stops being an optimization and becomes structurally necessary — a flat 140-tool catalog exceeds any client's routing ability, and some services (Protect is the worked example: AuthN vs Registration need different predictors; legacy RiskLevels+Overrides vs preferred Mitigations/Targeted Policies need a method decision before any tool call) require task clarification a flat catalog cannot express. Three scaling mechanisms, in the order they earn their complexity:

  1. Dynamic specialist exposure (shipped). The client sees a fixed 3-tool surface; specialists are data — one *.specialist.json per specialist, loaded from specialists/ (product set, versioned) plus a local overrides directory on a 30s TTL. Adding or retracting a specialist is a file operation, with no redeploy, no server restart, and no client renegotiation — verified live in both directions. The registry's curation stays hand-authored on purpose: a playbook is procedure, and procedure is the human contribution.
  2. Capability-based dispatch (designed, not yet needed). When specialist count grows past what any client should list, the client-facing contract shifts from one-tool-per-specialist to a stable capabilities() surface ("app+resource lifecycle", "directory", "flow debugging", …) with intent resolution moving behind it. The client's context load then scales with task domains, not tool count — the same law that pushes the raw catalog toward tool-search one layer down.
  3. Derived specialists (the end state): when P1 publishes the catalog metadata this proposal asks for (tool groupings, doc bindings, elicitation hints), specialists become assembled — subset from the domain's tool group, context from the doc binding, clarification from the hints — with the hand-written playbooks remaining as the seed corpus. The authored registry here is the stepping stone, not the end state.

Why this wins on context and cost

  • Client context. The orchestrating agent holds 2 tool one-liners instead of 78 full schemas — and the playbooks never enter the client's context at all.
  • Specialist context is bounded and disposable. Each run starts fresh with its subset and procedure; the orchestrator only accumulates compact summaries, while a flat setup accumulates every intermediate API response.
  • Model tiering is a config decision. Specialists inherit the deployment's model by default; each specialist can pin a cheaper tier in the registry. Routing (the client's model) stays expensive; execution doesn't have to be.
  • Upstream-proof. Ping adds tool #79 → the deny list recomputes. Nothing in this repo changes.

Local is the demo; hosting is Product's call

The install story is the composition story: attach one server, nothing else. The orchestrator is itself an MCP client of both services — the PingOne MCP Server (tools, authenticated) and the Docs MCP service (knowledge, auth-free) — and composes them at dispatch: the specialist's doc context arrives distilled in its prompt, so no specialist ever runs retrieval, and the client never attaches either upstream service. One claude mcp add, three fixed tools, two composed services.

This reference implementation ships as a local stdio MCP server for one admin — deliberately. Hosting was explored and the finding matters: a hosted orchestrator that serves one environment and effectively one identity gains nothing over local, and multi-user deployment raises decisions that belong to the product team (per-user token stores against a configured login env, ingress auth, a destructive-op deny-gate, idempotency). The specialist pattern is the contribution; the deployment topology is theirs to choose.

Attach claude mcp add p1-orchestrator … mcp add --transport http https://orchestrator/mcp

Auth admin OAuths once per machine (pre-wired client, token+URL agree by construction) per-caller tokens against a configured login env (URL no longer implies it); ingress auth in front
Trust chain Identical in both: P1-minted admin-person token → PingOne checks admin roles → P1 MCP checks per-env enablement → secret refusal. The layer adds narrowing, never bypass; audit attribution stays with the person.

What hosting adds (the graduation checklist, not a rework): per-user token storage keyed by caller · ingress auth (org SSO/mTLS) · a deny-gate for destructive ops (the one boundary P1's enforcement can't express — it knows who may act, not what this service should do) · idempotency keys on 25s tool calls · centralized run-log forwarding · concurrency caps. None of it reworks the architecture: the registry, the loops, and the visibility are deployment-agnostic by construction.

What we're asking of the product team

  1. Endorse the pattern, not the implementation. The PingOne MCP Server stays exactly what it is — raw tool supply. The intent layer composes because the auth model composes. We're asking that official guidance treat "wrap it" as a supported consumption mode — and that hosting decisions (multi-user, multi-env) come from Product, informed by the graduation checklist above rather than prescribed by us.
  2. Keep the pre-wired OAuth client (pingone-mcp-server) — it is what makes layered clients possible with zero registration ceremony. Document it.
  3. Consider shipping the routing metadata the catalog lacks — two publishable forms, both demonstrated from working code:
    • A topic map (task/tool → the 1–3 authoritative doc pages that decide it). We maintain a local workaround today (corpus.ts): 16 curated pins, live-fetched as .md alternates at call time, freshness-checked by npm run pin-check. It works — but it's hand-curation that duplicates what Ping could publish natively, and specialists shouldn't need to re-derive which pages decide.
    • Per-tool doc bindings in the MCP catalog — a docs field on each tool description (createApplication → applications-1.md + token-exchange-grant-type.md). One line per tool; closes the loop inside the catalog itself.

    The docs corpus itself is already excellent and agent-ready (llms.txt, .md alternates, docs-for-agents guide) — and the docs MCP service now under development is the retrieval tier our orchestrator already calls. The missing binding is which pages matter for which action: hand that over, and the local pins demote to overrides while the learnings tier (runtime-discovered constraints the docs lack — see the worked proof above) becomes the feedback channel into your corpus.

  4. A composite-tool escape hatch. Where a flow turns out fully deterministic (this app-creation sequence is close), a single composite tool with no LLM in the middle is even cheaper. The server could ship such composites natively.

Honest limits

  • One extra LLM hop per dispatch. Trivial single-call tasks lose; multi-step workflows win. The probe data here covers the multi-step cases — where the win is real.
  • Routing quality = description quality. The one-liner is the whole routing surface; crisp wording matters, and two specialists with overlapping scopes would fight.
  • Static subsets need curation. Deny-complement filtering survives upstream additions automatically, but a new tool that belongs in a subset still needs a registry edit — that's a feature (curation is the point), not a bug.
  • Latency. 20–31s per specialist run is fine for admin workflows, wrong for interactive chat loops.
  • Model non-determinism is real. The same context can be weighed differently across runs (one A/B still reasoned worker-first and self-recovered). Curation reduces the surface for this; it cannot eliminate it — which is why destructive-op enforcement belongs in infrastructure, not in prompts.
